# AI 编程中的进程管理：让 Agent 真正接管开发现场

> 定位：面向 AI 编程 Agent 用户的产品介绍/演示口播稿
>
> 建议时长：约 6 分钟
>
> 说明：`【画面】` 为制作提示，不需要口播；引号内内容为建议直接朗读的台词。

## 片头：问题从哪里开始

【画面】开发者在编辑器里让 Agent 启动项目，终端窗口逐渐变多。

“你有没有遇到过这样的情况？

你让 AI Agent 启动一个前端开发服务器。过了一会儿，它又启动了一次。结果端口被占用，浏览器打开的是旧进程，Agent 还在对着另一个进程排查。

接着你问：‘刚才那个服务到底启动成功了吗？’ Agent 说它已经执行了命令，但真正的报错在另一个终端窗口里。你只能自己切回终端，翻几百行输出，再把错误复制给 Agent。

如果项目还包含数据库、后端、前端和测试 watcher，情况会更复杂：进程散落在不同终端，谁启动的、还活不活着、日志在哪儿、该怎么重启，全都要靠人工记忆。

这不是 AI 不会写代码，而是它缺少一个可靠的‘进程工作台’。”

## 痛点：AI 编程为什么总卡在运行环节

【画面】四个关键词依次出现：重复启动、日志断裂、生命周期失控、多进程难协作。

“第一，重复启动。

Agent 每次接到任务，都可能重新执行 `npm run dev`、`docker compose up` 或测试命令。没有统一的进程记录，它很难判断现有服务是否已经在运行，也很难复用原来的实例。

第二，日志断裂。

命令执行成功，不代表服务启动成功。真正有价值的信息通常在 stdout 和 stderr 里：端口冲突、环境变量缺失、数据库连接失败，往往只出现一行。普通对话很容易丢掉这些上下文，Agent 也就无法根据证据继续修复。

第三，生命周期失控。

开发结束后，后台进程还在占用端口；下一次任务又叠加一批新进程。重启、停止、清理，最后变成手动查 PID、手动发送信号。

第四，多进程难协作。

前端要等后端 ready，订单服务要等库存服务；多个进程的日志还要放在一起看。只靠几个终端窗口，很难稳定编排和定位问题。”

## 解决方案：procm-mcp 做了什么

【画面】展示 Agent、procm-mcp、多个开发进程之间的关系图。

“procm-mcp 是一个专门给 AI Agent 使用的进程管理 MCP 服务器。

它把 Agent 启动的开发服务器、脚本、容器和 watcher 统一托管起来。每个进程都有可追踪的 ID、状态、工作目录和输出流。

Agent 可以启动进程，也可以列出当前进程、查看详情、重启、停止或删除。更关键的是，Agent 不需要猜服务发生了什么，它可以直接读取 stdout 和 stderr，查看最近日志，或者用正则搜索错误、警告和特定请求。

这些日志既能实时查看，也会保留历史文件。即使对话已经翻页，排查仍然有证据可用。任务结束时，procm-mcp 还会负责清理它创建的进程，减少‘上一次启动的服务还留在后台’这种问题。

对于固定项目，还可以在 `procm-commands.json` 里定义 `dev`、`test`、`db` 这样的命名命令。之后 Agent 只需要按名称启动，不必每次重新拼接整条命令。

当项目有多个服务时，可以用批量进程操作统一启动或重启；使用 room 和结构化日志，还能把同一组进程的消息聚合起来，按成员、级别或 trace ID 筛选。”

## 场景一：启动开发环境，不再重复开服务

【画面】Agent 对话框输入请求，随后展示进程列表和状态。

“先看最常见的开发场景。

你可以直接对 Agent 说：

‘检查当前项目已经托管的进程。如果前端和后端没有运行，就分别启动它们；不要重复启动已有实例。启动后告诉我进程 ID 和端口。’

Agent 会先读取进程状态，再决定是复用、启动，还是重启。你看到的不再是一串孤立的终端命令，而是一组有名字、有状态、可继续操作的开发服务。

如果团队已经配置了命名命令，也可以说：

‘列出 procm-commands.json 里的命令，启动 dev 和 db，并返回每个命令的运行状态。’

这特别适合每天反复进入同一个项目的场景。”

## 场景二：服务报错，让 Agent 直接读证据

【画面】浏览器请求失败；Agent 调用日志工具并定位到错误行。

“第二个场景是失败排查。

假设页面返回 500。你不需要打开终端、复制日志，只要告诉 Agent：

‘查看后端最近 50 条 stdout 和 stderr，搜索 error、exception 和 timeout，判断这次 500 的直接原因。’

Agent 可以先 tail 最近输出，再用正则同时搜索两个流，并按时间顺序整理结果。找到原因后，你还可以继续说：

‘修复代码后重启后端，确认新进程启动成功，并再次检查最近日志。’

这样形成的是一个闭环：读取证据、修改代码、重启验证，而不是执行命令后把结果丢在某个终端里。”

## 场景三：多服务联调与自动化测试

【画面】前端、API、worker、数据库四个进程组成一个 room，日志按服务筛选。

“第三个场景是多服务联调和自动化测试。

比如一个订单系统需要同时启动 API、库存服务和 worker。你可以让 Agent：

‘把这三个服务加入同一个 room，按依赖顺序启动；等待 API 和库存服务 ready，再运行集成测试。如果失败，汇总各服务最近的错误日志。’

procm-mcp 可以批量启动或重启多个进程，也能通过 room 聚合结构化日志。某个服务失败时，Agent 看到的是一组带来源、级别和时间的日志，而不是混在一起的文本。

这让本地联调、测试 watcher、Docker Compose，以及需要长时间运行的自动化任务，都有了统一的控制入口。”

## 如何开始使用：把意图交给 Agent

【画面】展示 MCP 配置已加载，随后切换到自然语言请求。

“使用方式很简单。安装和 MCP 配置可以直接交给你的 Agent 完成，你主要需要描述目标和约束。

之后记住四类常用请求：

第一，‘列出当前进程，告诉我哪些正在运行。’

第二，‘启动这个项目的开发服务，并返回进程 ID。’

第三，‘读取这个进程的 stdout 和 stderr，搜索某个错误。’

第四，‘重启、停止或清理指定进程，并确认结果。’

为了让结果更稳定，请在请求里说清楚项目目录、命令、服务之间的依赖，以及是否允许重启。例如：

‘在 `/workspace/shop` 中启动后端，使用现有 dev 命令；如果已有同名进程就复用，不要重复创建；启动后读取最近 20 条 stderr，根据进程状态和启动日志确认服务正常。’

Agent 负责调用工具，你负责表达目标。进程状态、日志和清理交给 procm-mcp 统一管理。”

## 收尾：把时间留给真正的开发

【画面】终端窗口收拢，Agent 输出“服务已启动，日志无错误”。

“AI 编程的瓶颈，很多时候不在写出第一行代码，而在让代码稳定地运行起来。

重复启动、找不到日志、忘记清理、多服务难协作，这些问题本来不该占用你的注意力。

procm-mcp 把进程启动、状态管理、日志读取、重启清理和多进程协作，变成 Agent 可以理解、调用和验证的一套能力。

当 Agent 能看到完整的运行现场，它才真正拥有完成任务所需要的上下文。

下次让 AI 帮你开发时，不妨先问一句：‘你能不能接管这个项目的进程和日志？’”
