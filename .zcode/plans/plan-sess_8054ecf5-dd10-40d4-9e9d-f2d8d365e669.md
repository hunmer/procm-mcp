## Bug: "Clear all" leaves some processes in the list

### Root cause
`handleClearAll` (App.tsx:285) fans out N parallel `DELETE /api/processes/:id` requests via `Promise.allSettled`. Each `deleteProcess` → `repo.remove()` (processes-repository.ts:99) does `await db.read() → splice → await db.write()`. lowdb (`Low.js`) does **not** serialize the read-modify-write cycle — `steno` only makes the final rename atomic. So all N deletes read the same full snapshot, each removes only one row from its *own* in-memory copy, and the last `db.write()` wins — persisting a snapshot that still contains every row except one. The `{"deleted":true}` response is correct (the in-memory `processes` array is spliced), but the very next WS broadcast calls `listProcessRecords()` → `repo.getAll()`, which reads back the *surviving persisted rows*, so they reappear in the UI.

### Fix: server-side bulk delete (single critical section)
Add a dedicated endpoint that deletes a set of ids in one transactional pass, so the in-memory array and the JSON store stay consistent, then have the dashboard call that instead of fanning out.

**1. `src/process-manager.ts`** — add `deleteProcesses(ids: string[])`:
- Do all the `killProcess` work first (these are independent and already concurrent-safe — they kill by PID, not index).
- After kills complete, splice **all** target ids out of the in-memory `processes` array in a single synchronous loop (no `await` between `findProcessIndex` and `splice`, so no interleaving), and clear their `startedAtByMeta` entries.
- Remove **all** target ids from the durable store in one `repo.removeMany(ids)` call (single read-modify-write).
- Emit `emitProcessChange()` exactly once at the end.
- Returns `{ deleted: string[]; notFound: string[] }`.

**2. `src/processes-repository.ts`** — add `removeMany(ids)`:
- One `db.read()` → build an id set → filter the array in place → one `db.write()`. This is the critical section that the per-id `remove()` violates under concurrency. Existing `remove()` is kept for single deletes (MCP tools etc.).

**3. `src/http-server.ts`** — add route `DELETE /api/processes` (no id param):
- Parse `{ ids?: string[] }` from the body.
- When `ids` is omitted/empty: treat as "delete all" — read current `listProcessRecords()` and collect every id (matches the dashboard's "clear all" intent).
- Call `deleteProcesses(ids)`, respond `{ deleted: [...], notFound: [...] }`.
- Placed alongside the existing `DELETE /api/processes/:id` branch; the `!idParam` guard already cleanly separates the collection-vs-item cases.

**4. `dashboard/src/lib/api.ts`** — add `clearAllProcesses(ids?: string[])` that `DELETE /api/processes` with a JSON body.

**5. `dashboard/src/components/App.tsx`** — rewrite `handleClearAll` to call the single bulk endpoint (no more `Promise.allSettled` fan-out). Keep the toast aggregating deleted/notFound counts.

### Why this approach
- Fixes the actual race at its source (the data layer), not a client-side retry/optimistic-removal band-aid.
- One WS broadcast after the bulk op, so the UI converges immediately.
- Keeps the existing single-id `DELETE /:id` untouched (MCP tools and per-row delete still work).
- Minimal blast radius: 2 small backend fns, 1 route, 1 api fn, 1 handler rewrite.

### Verification
- `npm run build` (runs `tsc` for backend + dashboard `tsc -b && vite build`) to confirm types compile.
- Manual: start several processes, hit Clear All, confirm the list empties and stays empty after the next WS push; check `processes.json` on disk has no leftover rows.

### Non-goals
- Not changing lowdb/steno; the read-modify-write race is inherent and the bulk path sidesteps it.
- Not touching `removeProcess` (mark-stopped/historical) — only the hard-delete path used by Clear All.
