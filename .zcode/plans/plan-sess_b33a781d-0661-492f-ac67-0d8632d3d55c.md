# WebSocket 实时推送改造方案

## 总体思路
把前端 3s 轮询改成 WebSocket 实时推送。后端原生 `http.Server` 上挂一个 `ws` 的 `WebSocketServer`（同端口、同 `127.0.0.1`），后端用一个轻量事件总线把"进程变化"和"新增日志"广播给所有连接；前端连 WS 后实时更新 React state，不再轮询。

经确认：**日志全量广播**（前端按当前选中进程/流过滤），**彻底移除轮询**（含 auto 3s 与手动 Refresh 的轮询语义；REST 接口保留作为初值加载与断线降级）。

## 一、后端改造（新增 `ws` 依赖）

### 1. 新增依赖
`package.json` 增加 `"ws": "^8.18.0"` 和 `"@types/ws"`（devDep）。`ws` 的 `WebSocketServer({ server })` 直接复用 `startHttpServer` 返回的 `http.Server`（`http-server.ts:333`），无需开新端口。

### 2. 新增 `src/events.ts` —— 轻量事件总线
用 Node `EventEmitter` 实现一个模块级单例总线（不引入新依赖，Node 自带）：
- `emitProcessChange()` —— 进程列表/状态变化
- `emitLog(processId, stream, chunk)` —— 新增单条日志
- 对外导出 `dashboardEvents` 总线与事件名常量 `PROCESS_CHANGE` / `LOG_APPEND`。
- 提供节流：`PROCESS_CHANGE` 用 ~50ms 合并窗口（避免 spawn→running 瞬间连发多条），但保证最终状态准确（最后一次 emit 一定广播）。

### 3. `src/process-manager.ts` —— 钩入进程状态变化点
- `applyProcessState()`（95-102 行）每次同步后调 `emitProcessChange()` —— 覆盖 spawn/exit/error 三处回调（104/110/116 行）。
- `pushProcess`（305）/`removeProcess` 的 splice（225）/`restartProcess` 的替换（247）后调 `emitProcessChange()`。

### 4. `src/process-stdout-client.ts` —— 钩入日志产生点
- `onData`（45 行）：在现有 `updateQueue.unshift(...)` 写库逻辑之外，**并行**调 `emitLog(id, type, { timestamp, message })` 广播（不阻塞写库；timestamp 用已有的 `Date.now()`）。
  - 注意：不改写库/磁盘逻辑，仅在内存层面多发一份给总线。

### 5. `src/http-server.ts` —— 接入 WebSocket
- `startHttpServer` 在 `server.listen` 成功后，调用新模块 `attachWebsocketServer(server, token)`。
- `verifyClient`（`ws` 选项）：若设置了 `token`，校验子协议或 query/首包里的 Bearer（与现有 `http-server.ts:102-109` 同源 token 逻辑一致）；未设 token 则放行。
- 收到连接后：
  - 连接时立即推送一次当前完整进程列表快照（让前端首屏不依赖 REST）。
  - 订阅 `dashboardEvents`：`PROCESS_CHANGE` → 广播 `{ type: "processes", data: listProcesses().map(toPublicView) }`；`LOG_APPEND` → 广播 `{ type: "log", processId, stream, data: { timestamp, message } }`。
  - 维护 `Set<WebSocket>` 连接集合，`ws.on("close"/"error")` 时取消订阅并从集合移除，避免泄漏。
- 消息格式统一为 JSON 信封：`{ type, ... }`。

## 二、前端改造（dashboard/）

### 1. 新增 `dashboard/src/lib/ws.ts` —— WebSocket 客户端 hook
导出 `useDashboardSocket()`：
- 用浏览器原生 `WebSocket`，连接同源 `/ws`（后端 `ws` 默认 path 为 `/`，前端连根路径即可；统一在同源）。
- 自动重连：断开后指数退避（1s→2s→…→10s 上限），重连成功后重新拉一次进程列表快照。
- 暴露：`status`（`connecting`/`open`/`closed`）、`onProcessUpdate(cb)`、`onLogAppend(cb)`。
- 返回的回调用 `useRef` 持有最新闭包，避免重连/重订阅。

### 2. `dashboard/src/components/App.tsx` —— 移除轮询，接 WS
- 删除 `auto`/`autoTimer` 状态（15/27 行）及 auto-refresh effect（57-68 行）和 checkbox（99-106 行）。
- 删除手动 Refresh 按钮改为"连接状态指示器"（绿点 open / 黄点 connecting / 红点 closed+重连倒计时）。
- `useDashboardSocket()`：`onProcessUpdate` 直接 `setData(...)` 并同步 `meta` 时间戳与 `selected`（保留原 37-39 行的 selected 同步逻辑）；初值仍用一次 `listProcesses()` REST（或依赖 WS 连接时的快照）。
- start/stop/restart 后的 `void refresh()`：改为乐观处理——操作成功后后端会自动 emit `PROCESS_CHANGE`，前端靠 WS 自动刷新；可保留一次轻量手动 `listProcesses()` 兜底。

### 3. `dashboard/src/components/LogPanel.tsx` —— 实时日志追加
- 保留初次拉取：切换 process/stream/count 时仍调一次 `getLogs()`（`api.ts:50`）取历史快照作为基底（25-49 行 effect 不变）。
- 新增：通过 App 透传或自行 `useDashboardSocket()` 监听 `onLogAppend`：当 `log.processId === process.id && log.stream === 当前 stream` 时，把 `[timestamp] message\n` **增量追加**到 `text` 末尾（取代当前的全量替换语义）。
- 切换 stream/process 时清空 `text` 重新拉快照（现有 effect 已处理）。
- 可选：`<pre>` 简单自动滚动到底（仅当用户已在底部时）。

## 三、验收与测试
- `npm run build`（后端 tsc）+ `npm run build:dashboard`（前端）双绿。
- 手动：`npm run start:server` 启动，浏览器打开 dashboard：
  1. 启动一个持续输出日志的进程（如 `ping` / 自写循环输出），确认进程列表与日志**实时刷新**、无 3s 延迟。
  2. stop/restart 进程，确认状态/日志实时变化。
  3. 关闭后端，确认前端显示"重连中"并在后端重启后自动恢复。
- 现有 REST 路由保持不变，不影响 MCP 与 CLI 客户端（`tests/http-api.mjs` 等应仍通过）。
